# TECHNICAL SPECIFICATIONS AND SYSTEM REQUIREMENTS (SRS)
# Project: MCU (Metal-CUDA Unit) Hybrid Transpiler

# This document defines the functional, non-functional, and architectural requirements for developing a Command Line Interface (CLI) utility capable of analyzing, validating, and transpiling NVIDIA CUDA source code into Apple Metal Shading Language (MSL) at runtime. The system uses a hybrid mapping strategy powered by a C++ Wrapper architecture.

# -----------------------------------------------------------------------------
# STAGE 1: CLI Architecture, Modularization, and Semantic Validation (Sanity Checking)
# -----------------------------------------------------------------------------

## 1.1 Objectives
* Isolate abstract syntax tree (AST) parsing logic from any graphical user interface components.
* Build a standalone CLI to act as the single entry point and orchestrator for the pipeline.
* Implement a static validation layer to catch critical hardware and logical violations before code generation.

## 1.2 Functional Requirements
* REQ-1.1.1: Independent CLI Interface
  The system must execute as a standalone terminal utility (named mcu), exposing two primary subcommands: check (structural analysis and semantic validation) and build (transpilation and native execution compilation).
* REQ-1.1.2: Decoupled Parsing Subsystem (AST)
  The parsing component leveraging libclang C++ bindings and the hybrid fallback regex scanner must be isolated into a dedicated package named core/. This module must output a clean, serializable metadata structure (e.g., a dictionary).
* REQ-1.1.3: Semantic Validation Module (Sanity Checker)
  The system must evaluate hardware boundaries prior to the code generation phase:
    * Compute the total number of threads per block (BlockSize = DimX * DimY * DimZ). If this total exceeds the Apple Silicon hardware threadgroup limit of 1024, the pipeline must halt immediately and return a critical error code.
    * Scan the kernel body for local execution barriers (__syncthreads()). If a barrier is detected inside a branching block dependent on thread indices (divergent execution paths), the system must raise a specific safety warning.

## 1.3 Non-Functional Requirements
* REQ-1.2.1: Input Error Handling
  If the target file contains native C++ syntax errors, the parser subsystem must catch the exceptions gracefully without crashing the parent CLI process, returning a formatted error report instead.
* REQ-1.2.2: Static Analysis Execution Time
  The parsing and validation phase for an average source file (up to 5,000 lines of code) must execute in under 250 milliseconds.


# -----------------------------------------------------------------------------
# STAGE 2: Transpilation Engine, MSL Generation, and the Kernel Routing Table
# -----------------------------------------------------------------------------

## 2.1 Objectives
* Transform the intermediate representation (AST metadata) into text-valid code complying with the Apple Metal Shading Language specification.
* Generate a dynamic lookup structure (Routing Table) to map host execution parameters to compiled runtime GPU functions.

## 2.2 Functional Requirements
* REQ-2.1.1: Argument List Translation
  The code generator must convert raw pointers targeting CUDA global memory (e.g., float*) into qualified Metal device pointers, injecting the correct buffer slot index qualifiers (device float* name [[buffer(N)]]). Value parameters must be mapped as constant references (constant int& name [[buffer(M)]]).
* REQ-2.1.2: Hardware Geometry Injection
  At the end of the argument signature for every transpiled kernel function, the engine must automatically append native Metal input attribute qualifiers for thread positioning: [[thread_position_in_grid]], [[threadgroup_position_in_grid]], [[threads_per_threadgroup]], and [[thread_position_in_threadgroup]].
* REQ-2.1.3: Kernel Body Mutation
  The engine must replace native CUDA implicit global variables (threadIdx, blockIdx, blockDim) with their mathematically equivalent expressions derived from the injected Metal attributes specified in REQ-2.1.2.
* REQ-2.1.4: Dynamic Kernel Routing Table Generation
  The generation engine must compile a Kernel Routing Table (serialized as a JSON map or embedded metadata array). This table must establish an explicit structural link between the CUDA kernel name, its index-to-argument signature mapping (e.g., Argument 0 -> [[buffer(0)]], Argument 1 -> [[buffer(1)]]), and its assigned Metal entry point function pointer generated for the runtime pipeline.

## 2.3 Non-Functional Requirements
* REQ-2.3.1: Syntactic Validity of Output
  The code written to the intermediate .metal file must comply with the C++14 standard (the structural foundation of MSL) and must compile via the native macOS metal compiler utility without requiring manual edits.


# -----------------------------------------------------------------------------
# STAGE 3: Optimization via Thread Coarsening
# -----------------------------------------------------------------------------

## 3.1 Objectives
* Implement a source-to-source compilation optimization layer designed to adjust compute density for optimal performance on Apple Silicon unified memory architectures.

## 3.2 Functional Requirements
* REQ-3.1.1: Coarsening Factor Parameterization
  The CLI must accept an optional configuration flag (`--coarsening [1|2|4|8]`) specifying how many logical CUDA X-axis threads are packed into one physical Metal thread. When omitted, build may automatically select 2, 4, or 8 to recover a statically known block above 1024 threads.
* REQ-3.1.2: Grid Geometry Rescaling
  When the factor is greater than 1, the launch orchestrator must preserve the threadgroup count and divide the physical X dimension of `threads_per_threadgroup` by the factor. The original X dimension must be exactly divisible by the selected factor.
* REQ-3.1.3: Instruction Multiplicity (Loop Unrolling)
  The code generator must wrap the kernel body in a fixed-factor loop and reconstruct logical `threadIdx` and `blockDim` values for every iteration, preserving CUDA indexing semantics.


# -----------------------------------------------------------------------------
# STAGE 4: C++ Runtime Integration (Wrapper Architecture & Routing Resolution)
# -----------------------------------------------------------------------------

## 4.1 Objectives
* Intercept and reroute NVIDIA CUDA Runtime API calls from the host application (CPU) to Apple's native Metal framework, querying the Routing Table to resolve memory slots and kernel entry points at runtime.

## 4.2 Functional Requirements
* REQ-4.1.1: Wrapper Interface Definition (cuda_to_metal.h)
  Develop a C++17 public header exposing dim3, cudaMalloc, cudaMemcpy, cudaFree, cudaDeviceSynchronize, error reporting, and typed kernel dispatch. The backend uses Apple's Objective-C++ Metal API, avoiding a vendored Metal-cpp dependency.
* REQ-4.1.2: Unified Memory Management (UMA Integration)
  The wrapper must map cudaMalloc calls directly to MTL::Device::newBuffer configurations using MTL::ResourceStorageModeShared. It must map cudaMemcpy calls to a native standard memcpy execution directly within the shared RAM, bypassing any virtual PCIe transfer overhead.
* REQ-4.1.3: Runtime Routing Table Resolution
  Standard C++ preprocessing cannot intercept CUDA triple-chevron grammar. The MCU host pass must rewrite both `kernel<<<grid, block>>>(args...)` and `cudaLaunch(kernel, grid, block, args...)` into typed runtime dispatch calls. The dispatcher queries a versioned routing table to resolve entry points and numeric buffer slots.
* REQ-4.1.4: Native Build Output
  `mcu build <path> --native --output <directory>` must emit generated.metal, routing_table.txt, transformed host sources, and a macOS executable linked with Metal and Foundation.
* REQ-4.1.5: Physical Geometry Enforcement
  Coarsening divides only runtime block.x. Grid dimensions remain unchanged. Dispatch rejects incompatible geometry and physical threadgroup volumes above the pipeline limit.

## 4.3 Non-Functional Requirements
* REQ-4.3.1: Shared Allocation Latency
  After warm-up, repeated 4 KiB shared-buffer allocations must report p95 latency below 2ms on the local Apple Silicon verification runner. The benchmark must report measurements rather than infer leak freedom from latency.


# -----------------------------------------------------------------------------
# STAGE 5: Architectural Refactoring and Source Diagnostics
# -----------------------------------------------------------------------------

## 5.1 Objectives
* Establish typed compiler boundaries and independently testable runtime components.
* Map native Metal diagnostics back to original CUDA source locations.

## 5.2 Functional Requirements
* REQ-5.1.1: Line Directive Injection
  During the text generation phase of the .metal source file, the compiler must insert a standard C preprocessor #line <original_cuda_line> "<filename>.cu" directive immediately before translating each logical block of instructions.
* REQ-5.1.2: Stderr Stream Interception and Parsing
  Metal and clang diagnostics must be parsed into structured records containing severity, message, file, line, and column.
* REQ-5.1.3: Native Metal Validation
  Native builds must compile generated MSL before host linking and fail with a source-mapped diagnostic when MSL is invalid.
* REQ-5.1.4: Component Boundaries
  Frontend, IR, passes, backends, build services, diagnostics, and runtime resource owners must expose explicit interfaces without duplicate implementations.


# -----------------------------------------------------------------------------
# STAGE 6: CUDA Symbol Graph, Device Functions, and Translation Registry
# -----------------------------------------------------------------------------

## 6.1 Objectives
* Replace kernel-only translation with a project-wide CUDA symbol model.
* Translate user-defined device helpers, types, constants, and dependencies into reusable MSL declarations.
* Establish a data-driven registry for known CUDA intrinsics without treating user functions as manually configured mappings.

## 6.2 Functional Requirements
* REQ-6.2.1: Typed Symbol IR
  The frontend must represent functions, parameters, structs, typedefs, enums, constants, qualifiers, source locations, and translation-unit ownership as typed symbols.
* REQ-6.2.2: CUDA Function Qualifiers
  The compiler must distinguish `__global__`, `__device__`, `__host__`, and combined `__host__ __device__` functions. Device-callable functions must be emitted as MSL helpers; dual functions must remain available to transformed host code when required.
* REQ-6.2.3: Device Call Graph
  The frontend must construct a call graph rooted at translated kernels, include every reachable device helper exactly once, and diagnose missing, recursive, ambiguous, or unsupported calls.
* REQ-6.2.4: Header and Type Lowering
  Project headers, typedefs, structs, fixed arrays, compile-time constants, and supported preprocessor definitions must be preserved or lowered into valid host C++ and MSL declarations.
* REQ-6.2.5: Multi-Translation-Unit Device Linking
  Kernels and device helpers may be defined in separate `.cu` files. MCU must resolve their declarations and definitions into one deterministic Metal module while retaining source mapping.
* REQ-6.2.6: Translation Registry
  Known CUDA intrinsics must be described by source symbol, supported signatures, category, required capability, target representation, and a named lowering handler. Unsupported overloads must fail with structured diagnostics.
* REQ-6.2.7: Build Symbol Manifest
  Each build must emit a compiler-facing symbol manifest containing translated user functions, call edges, used intrinsics, source locations, and capabilities. Runtime-only routing metadata must remain separate.
* REQ-6.2.8: Semantic Frontend Contract
  Stage 6 symbol extraction must use a semantic AST frontend as the authoritative source for declarations, canonical types, qualifiers, overload resolution, and call edges. Regex scanning may remain a compatibility fallback for Stage 1 checks, but it must not silently produce a Stage 6 native build when semantic information is incomplete.
* REQ-6.2.9: Address-Space Inference and Specialization
  The compiler must infer whether every device pointer is backed by device, constant, threadgroup, or thread-local storage. When one CUDA helper is valid for multiple address-space signatures, MCU must emit deterministic specialized MSL variants or reject the ambiguous call with a source-mapped diagnostic.
* REQ-6.2.10: Deterministic Symbol Identity
  Symbol IDs and generated MSL names must be derived from qualified names, canonical signatures, qualifiers, and specialization context. Output ordering and names must remain stable across identical builds.

## 6.3 Acceptance Requirements
* The CUDA SHA-256 helper chain must compile across headers and multiple `.cu` files.
* Known SHA-256 vectors must match an independent CPU reference.
* Missing device symbols and unsupported intrinsic signatures must report the original CUDA call site.
* Stage 6 native builds must fail instead of falling back to incomplete regex metadata when semantic resolution is required.


# -----------------------------------------------------------------------------
# STAGE 7: NVCC-Compatible Driver and Existing Makefile Integration
# -----------------------------------------------------------------------------

## 7.1 Objectives
* Allow existing CUDA build systems to invoke MCU without translating their Makefiles.
* Produce native macOS executables from CUDA/C++ projects through compiler-like commands.

## 7.2 Functional Requirements
* REQ-7.2.1: NVCC Driver Shim
  MCU must expose an `nvcc`-compatible driver entry point for the supported flag subset. `mcu make` must execute the existing build recipe with a temporary `nvcc` shim earlier in `PATH`.
* REQ-7.2.2: Compiler Flag Compatibility
  The driver must support input lists and the flags `-I`, `-D`, `-O0` through `-O3`, `-o`, `-c`, `-dc`, and `-Xcompiler` for validated host options. Unsupported flags must produce explicit diagnostics rather than being silently ignored.
* REQ-7.2.3: MCU Intermediate Objects
  Compile-only and relocatable-device-code invocations must emit versioned MCU object metadata. The final link invocation resolves MCU objects, native host objects, routing metadata, generated MSL, and runtime components into one executable.
* REQ-7.2.4: Native Compiler Commands
  The CLI must provide:
    * `mcu compile <sources...> [flags] -o <executable>`;
    * `mcu run <sources...> [flags] -- <program arguments...>`;
    * `mcu make [-C directory] [make arguments...]`.
* REQ-7.2.5: Existing Project Layout
  Include paths, relative working directories, generated files, nested Makefiles, and output target names must retain the semantics expected by the original build recipe.
* REQ-7.2.6: Incremental Build Cache
  Unchanged frontend IR, Metal libraries, and runtime objects should be reused through content-addressed cache keys that include sources, headers, compiler flags, MCU version, and target SDK.
* REQ-7.2.7: Precompiled Runtime Metal Library
  Normal native executables must load a linked `.metallib` and must not compile MSL source at startup. Runtime source compilation may exist only as an explicit diagnostic fallback.
* REQ-7.2.8: Build Timing and Cache Metrics
  Compile and make commands must report named frontend, device-link, Metal compile, host compile, native link, cache lookup, and total phases. Cold, warm, no-op, and incremental measurements must be distinguishable.
* REQ-7.2.9: Dependency-Compatible Make Integration
  The NVCC driver subset must support dependency-file options required for correct incremental Make builds and must preserve working-directory-relative paths and argument ordering.
* REQ-7.2.10: Validated Native Link Flags
  The NVCC-compatible link mode must accept and safely forward the documented `-l` and `-L` subset required by existing Makefiles. Link-only flags must not silently alter compile-only invocations.

## 7.3 Acceptance Requirements
* An unchanged multi-file Makefile that invokes `nvcc -dc` must build through `mcu make`.
* The resulting Mach-O executable must locate its Metal artifacts and run without Python or environment variables.
* A normal run must perform zero runtime MSL source compilations.
* The current small fixture must meet the documented Stage 7 cold, warm, no-op, incremental, and startup performance budgets.


# -----------------------------------------------------------------------------
# STAGE 8: Core CUDA Memory, Synchronization, and Atomic Parity
# -----------------------------------------------------------------------------

## 8.1 Objectives
* Support the CUDA features required by reductions, hashing pipelines, and concurrent result selection.

## 8.2 Functional Requirements
* REQ-8.2.1: Threadgroup Memory
  Static and dynamic `__shared__` declarations must map to Metal threadgroup memory with alignment, index, and byte-size metadata.
* REQ-8.2.2: Typed Atomics
  Supported forms of atomicAdd, atomicCAS, atomicMin, atomicMax, and atomicExch must be selected by value type and address space. Unsupported combinations must fail validation.
* REQ-8.2.3: Barrier Semantics
  Synchronization lowering must preserve threadgroup visibility and reject divergent barriers that cannot be executed safely.
* REQ-8.2.4: Runtime Memory Operations
  Add validated cudaMemset behavior and the additional synchronous memory-copy forms required by supported projects.
* REQ-8.2.5: Local Arrays and Pointer Operations
  Device code must support fixed local arrays, pointer offsets, supported casts, and byte-oriented operations required by hashing implementations.
* REQ-8.2.6: CUDA Array Parameter Decay
  CUDA/C array syntax in function parameters must canonicalize to pointer semantics while struct fields and local fixed arrays retain array semantics. Equivalent array/pointer declarations must resolve to one canonical device symbol.
* REQ-8.2.7: Complete Device Call Graph
  Every reachable device call must resolve to a user function, a typed translation rule, or a source-mapped unsupported diagnostic before MSL emission. Unsupported AST nodes must not cause valid neighboring calls to disappear silently.
* REQ-8.2.8: Expression Address-Space Preservation
  Pointer arithmetic, dereferences, C-style casts, supported reinterpret casts, local arrays, and struct fields must preserve or explicitly validate device, thread, threadgroup, and constant storage classes.
* REQ-8.2.9: Atomic Access Model
  Atomic lowering must mark atomic pointees and rewrite both atomic operations and non-atomic CUDA accesses to legal MSL atomic accesses with explicit memory ordering.
* REQ-8.2.10: Coarsening and Synchronization Safety
  Kernels using shared memory or threadgroup barriers must not be coarsened unless equivalence of logical CUDA participants and physical Metal synchronization participants is proven.
* REQ-8.2.11: Diagnostic Severity Integrity
  Semantic frontend errors must remain build-blocking errors in human and JSON output. Presentation must never relabel a compiler error as informational.

## 8.3 Acceptance Requirements
* A shared-memory reduction must match a CPU reference.
* A 20,000-thread atomic winner/counter test must complete without lost updates.
* Original-style SHA helpers using array parameters, fixed local arrays, byte casts, and device memset must match standard vectors exactly.
* A repository-owned Merkle/nonce fixture must match independent CPU roots and smallest-valid-nonce results.
* The external assignment source set must reach a native build without Metal-specific source changes; full assignment input/output equivalence remains Stage 9.


# -----------------------------------------------------------------------------
# STAGE 9: Native CUDA Project Compatibility Milestone
# -----------------------------------------------------------------------------

## 9.1 Objectives
* Demonstrate that MCU can build and run a representative CUDA project on macOS without source rewrites specific to Metal.

## 9.2 Functional Requirements
* REQ-9.2.1: Assignment-Scale Integration
  A multi-file SHA-256, Merkle-tree, and Proof-of-Work project must build through `mcu make` using its existing CUDA-oriented Makefile.
* REQ-9.2.2: Numerical and Byte-Level Equivalence
  SHA-256 vectors, Merkle roots, selected nonces, and resulting block hashes must match independent CPU reference outputs exactly.
* REQ-9.2.3: Native Execution Contract
  The generated program must be a native macOS executable using Metal internally. It must accept the original command-line arguments and preserve expected input/output file behavior.
* REQ-9.2.4: Performance Reporting
  Verification must report translation time, native build time, JIT or library-load time, Merkle execution time, nonce-search time, and total runtime. Correctness thresholds and performance benchmarks must remain separate.
* REQ-9.2.5: Repository-Owned Oracle Fixture
  CI must use a self-contained multi-translation-unit fixture and an independent CPU oracle. External coursework or private repositories may be audited manually but must not be CI dependencies.
* REQ-9.2.6: Build Compatibility Matrix
  Verification must cover clean Make builds, separate device compilation, final link, unchanged/no-op invocation, cached relink, and invalidation after one CUDA translation unit changes.
* REQ-9.2.7: Deterministic Execution
  At least five executions of one native artifact must produce identical non-timing output fields and byte-identical SHA-256, Merkle root, nonce, and final hash results.
* REQ-9.2.8: Opt-In Runtime Metrics
  Native executables must optionally emit a versioned JSON sidecar containing device initialization, artifact loading, pipeline creation/cache, memory-copy, command-submission, GPU-execution, synchronization, byte-count, dispatch-count, and process-total measurements without changing application stdout.
* REQ-9.2.9: Scope Integrity
  Stage 9 compatibility work must remain independent of any one application algorithm. Missing CUDA semantics must produce source-mapped diagnostics and be implemented in their owning semantic stage rather than patched into the reference workload.

## 9.3 Acceptance Requirements
* The repository fixture must build through `mcu make` without source edits.
* Public fixture inputs must match an independent CPU oracle exactly.
* The executable must run without Python, MSL JIT, or mandatory environment variables.
* Runtime metric collection must be opt-in, schema-versioned, and covered by a native test.


# -----------------------------------------------------------------------------
# STAGE 10: Asynchronous Streams and Command Scheduling
# -----------------------------------------------------------------------------

## 10.1 Functional Requirements
* REQ-10.1.1: Stream Lifecycle
  Implement cudaStreamCreate, cudaStreamDestroy, and cudaStreamSynchronize.
* REQ-10.1.2: Asynchronous Operations
  Implement supported cudaMemcpyAsync and asynchronous kernel submission while preserving in-stream ordering.
* REQ-10.1.3: In-Flight Resource Ownership
  Buffers and pipeline resources must remain valid until every referencing command completes. cudaFree must not invalidate in-flight work.
* REQ-10.1.4: Concurrency Contract
  Independent streams may progress independently, but physical overlap is hardware-dependent and must be reported as a benchmark rather than guaranteed.
* REQ-10.1.5: CUDA Launch Configuration
  The fourth triple-chevron configuration value must lower to an opaque typed stream handle while preserving dynamic shared-memory bytes as the third value.
* REQ-10.1.6: Async Copy Staging
  Supported H2D, D2D, and D2H asynchronous copies must use ordered Metal commands and retain staging storage until synchronization. Unsupported pageable H2H async behavior must fail explicitly.
* REQ-10.1.7: Deferred Error Attribution
  Metal failures discovered after submission must retain the originating kernel or copy operation and surface through stream or device synchronization.
* REQ-10.1.8: Performance Corpus
  Repository-owned easy, medium, hard, and stress scheduler workloads must emit versioned metrics suitable as unchanged Stage 14 optimization baselines.

## 10.2 Acceptance Requirements
* One-stream producer/copy/consumer chains must be deterministic.
* Explicit streams must preserve local order without accidental mutual waits.
* `cudaFree`, stream destruction, and device synchronization must not release in-flight resources.
* A 100-launch benchmark must compare per-launch synchronization with one batched wait and preserve exact output.


# -----------------------------------------------------------------------------
# STAGE 11: CUDA Library Adapters and Apple Acceleration Frameworks
# -----------------------------------------------------------------------------

## 11.1 Functional Requirements
* REQ-11.1.1: Adapter Registry
  Introduce routing schema version 2 and an extensible registry separating CUDA library symbols from native Apple adapter implementations. Existing kernel-only routes from schema version 1 must continue to load through an explicit compatibility path.
* REQ-11.1.2: Library Call IR
  Represent resolved CUDA library calls with typed symbols, argument roles, source locations, required runtime ABI, and adapter capability requirements.
* REQ-11.1.3: First cuBLAS Adapter
  Implement a validated cuBLAS subset: cublasCreate, cublasDestroy, cublasSetStream, cublasGetStream, and cublasSgemm. The SGEMM adapter must preserve transpose, dimensions, leading dimensions, alpha, beta, status values, pointer-mode validation, column-major indexing, and Stage 10 stream association.
* REQ-11.1.4: Apple Acceleration Backend
  Map the supported cublasSgemm subset to MPSMatrixMultiplication or a proven faster Metal implementation after the semantic adapter is stable, with adapter-owned caching for reusable descriptors, framework state, and temporary buffers where valid.
* REQ-11.1.5: Library Diagnostics
  Unsupported library versions, symbols, data types, and modes must fail with source-mapped diagnostics.
* REQ-11.1.6: Capability Staging
  cuRAND, cuFFT, and Thrust-like primitives must be represented in the capability table as unsupported or planned entries until implemented. Adapter code remains in the main compiler/runtime repository; large private compatibility corpora and long-running benchmarks may live in separate private repositories.

## 11.2 Acceptance Requirements
* Non-library Stage 1-10 projects must build and run unchanged after routing schema version 2 is introduced.
* A 128x128 cublasSgemm fixture must match an independent CPU reference within a documented epsilon.
* A 2048x2048 cublasSgemm fixture must report adapter setup, temporary allocation, copy, queueing, GPU execution, and total timing metrics.
* Stream-bound SGEMM calls must respect Stage 10 stream ordering.
* Unsupported library calls must report the original CUDA source location.

* REQ-12.1.5: Runtime API Diagnostics
  Unsupported runtime APIs, flags, device IDs, and invalid handles must fail explicitly with CUDA-like error codes and diagnostics.

## 12.2 Acceptance Requirements
* CUDA files using supported cuda_runtime.h APIs and no auxiliary libraries must compile and run through mcu compile without source edits.
* Device property reporting must be conservative and truthful for Apple Silicon.
* Event timing must work across kernels and asynchronous memory operations.
* Runtime API capability data must be ready for Stage 13 reporting.


# -----------------------------------------------------------------------------
# STAGE 13: Stable Tooling API and IDE Integration
# -----------------------------------------------------------------------------

## 13.1 Functional Requirements
* REQ-13.1.1: Stable JSON Contracts
  Freeze a versioned public JSON envelope for check, build, compile, run, make,
  nvcc-driver, capabilities, and analyze commands. Every public JSON payload must
  expose schema_version, contract, mcu_version, diagnostics, and exit_status.
* REQ-13.1.2: Capability Reporting
  Expose `mcu capabilities` as a machine-readable report of supported CUDA
  syntax, runtime APIs, intrinsics, compiler flags, target constraints, and
  library adapters. Unsupported/planned major CUDA features must be explicit.
* REQ-13.1.3: Exit Status Contract
  Exit status 0 means success, 1 means source/semantic/translation/native
  failure caused by project input, and 2 means infrastructure, missing path,
  missing toolchain, filesystem, or invocation failure. `mcu run` may preserve
  the executed program's exit status but must classify it as program_failure in
  JSON.
* REQ-13.1.4: IDE Backend
  Provide `mcu analyze` as the stable editor/checker analysis entry point
  without coupling compiler components to editor-specific code. A future daemon
  or LSP must reuse this contract instead of creating a separate schema.
* REQ-13.1.5: Contract Tests
  Add tests that pin the Stage 13 envelope, capability report, analyze command,
  runtime API visibility, library adapter visibility, and invalid-path behavior.


# -----------------------------------------------------------------------------
# STAGE 14: Warp/SIMDGroup Semantics and CUDA Graphs
# -----------------------------------------------------------------------------

## 14.1 Functional Requirements
* REQ-14.1.1: Logical CUDA Warp Model
  Supported warp intrinsics must preserve CUDA's logical 32-lane masks, active-lane behavior, convergence, and return values. Direct Metal simdgroup mapping is allowed only for validated equivalent target widths.
* REQ-14.1.2: Typed Warp Intrinsics
  Shuffle, ballot, any/all, lane-mask, and sync operations must be selected by signature, mask semantics, and target capability. Unsupported divergent cases must fail explicitly.
* REQ-14.1.3: CUDA Graph DAG
  Supported kernel, copy, and memset graph nodes must preserve dependency ordering, parameter ownership, stream association, resource lifetime, and deterministic replay.
* REQ-14.1.4: Graph Lifecycle
  Graph creation/capture, instantiation, repeated launch, supported update, and destruction must expose CUDA-compatible status and failure behavior for the documented subset.


# -----------------------------------------------------------------------------
# STAGE 15: Performance Engineering and Autotuning
# -----------------------------------------------------------------------------

## 15.1 Functional Requirements
* REQ-15.1.1: Reproducible Performance Baselines
  Every optimization must report target hardware, SDK, MCU revision, cold/warm state, median, p95, and correctness result against an unchanged reference workload.
* REQ-15.1.2: Safe Autotuning
  Geometry, coarsening, specialization, and scheduling candidates must be rejected on timeout, crash, output mismatch, or unstable measurements. Conservative deterministic defaults must remain available.
* REQ-15.1.3: Compiler and Runtime Optimization
  Optimize incremental compilation, Metal/pipeline archives, memory reuse, command batching, graph replay, and synchronization only after the corresponding semantics are covered by Stage 1-14 tests.
* REQ-15.1.4: Explainable Decisions
  MCU must expose selected tuning parameters, cache decisions, target assumptions, and fallback reasons in human and machine-readable metrics.
