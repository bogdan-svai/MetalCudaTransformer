# SOFTWARE REQUIREMENTS SPECIFICATION (SRS)
# SYSTEM LAYER: STAGE 16 - COMMAND BUFFER BATCHING
# -----------------------------------------------------------------------------

## 1. Objective

Stage 16 reduces Metal submission overhead by encoding consecutive kernels from
one CUDA stream into one command buffer. Correct CUDA ordering and deferred
error behavior remain mandatory.

## 2. Safety contract

- A batch belongs to exactly one CUDA stream and its Metal command queue.
- Async copies, cuBLAS work, stream/device synchronization, resource release,
  and cross-stream legacy-default ordering flush outstanding kernel batches.
- A stream is never destroyed with an uncommitted batch.
- Kernel dispatch counters remain per launch; command-buffer and batch counters
  describe physical Metal submissions.
- GPU timing for a repeated kernel in one batch is reported once for the batch,
  avoiding multiplication of the command-buffer duration by launch count.

## 3. Acceptance

- Existing stream, event, graph, cuBLAS, memory, and error tests remain green.
- The medium and hard multi-launch tiers submit fewer command buffers than
  logical kernel dispatches.
- Stage 10 performance and large-kernel regression budgets remain green.

## 4. Initial Apple M4 Max result

Three-sample validation on 2026-09-06 passed all Stage 10 budgets:

- 10 launches: 3.493x median batched-vs-synchronous speedup;
- 100 launches: 14.719x median speedup and 104 command buffers for the combined
  synchronous/batched comparison;
- 1,000 launches: 34.729x median speedup and 1,004 command buffers for the
  combined comparison;
- one large launch: 1.065x median speedup, with no large-kernel regression.

The comparison intentionally contains a synchronous half that flushes every
launch. The batched half collapses consecutive kernels at synchronization
boundaries; therefore combined command-buffer counts do not represent the
batched half alone.

## 5. Stage 16B - bounded staging-buffer reuse

Async H2D and D2H copies reuse completed shared Metal buffers using a
best-fit pool. Recycling occurs only after the owning command buffer completes
and after deferred D2H publication. The pool retains at most 16 buffers and
64 MiB; larger or excess buffers are released. Runtime counters expose hits,
misses, and evictions. A repeated-copy integration test demonstrates two cold
allocations followed by at least six cache hits while preserving exact output.

## 6. Stage 16C - persistent semantic IR cache

Semantic projects are cached as checksummed JSON through the existing CacheStore.
The key includes MCU version, compile context, absolute source paths, and SHA-256
content digests. The cache reconstructs typed functions, calls, effects, local
objects, statements, declarations, and macros; source changes invalidate the
entry. A representative four-file project reduced frontend time from 69.9 ms
to 20.6 ms across separate processes (local measurement).

## 7. Default-stream compatibility

The legacy/default CUDA stream keeps single-submit behavior: its kernel batch is
flushed immediately after dispatch. Explicit streams retain command-buffer
batching. This isolates the optimization from the Stage 10 launch-only baseline
while preserving measured gains for asynchronous explicit-stream workloads.
