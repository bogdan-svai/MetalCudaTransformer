# SOFTWARE REQUIREMENTS SPECIFICATION (SRS)
# SYSTEM LAYER: STAGE 2 - TRANSPILATION ENGINE, MSL GENERATION & ROUTING TABLE
# -----------------------------------------------------------------------------

## 1. MODULE OVERVIEW & ARCHITECTURAL OBJECTIVES
The primary objective of Stage 2 is to architect the core Source-to-Source (S2S) translation engine capable of converting structurally validated NVIDIA CUDA kernel functions into specification-compliant Apple Metal Shading Language (MSL) source code. 

Additionally, this stage establishes the runtime connection layer by generating a deterministic "Kernel Routing Table". This table serializes argument-to-buffer slot mappings, enabling the downstream C++ host runtime framework (Stage 4) to dynamically bind memory and invoke translated device functions without ahead-of-time binary linking.

## 2. SYSTEM ARCHITECTURE & PIPELINE EXPANSION
Stage 2 introduces the `build` pipeline orchestrator. It expands the structural workflow by ingesting the serialized abstract syntax tree (AST) layout metadata and emitting both code and routing signatures inside the sandboxed container:

  [Stage 1 Validated Metadata] ---> core/transpiler.py ---> generated.metal
                                                        ---> routing_table.txt
                                                        ---> mcu_artifacts.zip

### 2.1 Component Extensions:
* core/transpiler.py: The compilation engine. Responsible for signature mapping, address space conversion, and implicit hardware variable translation.
* mcu (Build Command): Activated execution lane supporting `./mcu build <source_file>`. Automatically triggers Stage 1 checking policies prior to running transpilation.

## 3. DETAILED FUNCTIONAL REQUIREMENTS

### 3.1 CLI Build Execution Target
* REQ-2.1.1: Unified Build Pipeline Routing
  The main orchestration binary must accept the `build` subcommand: `./mcu build <path_to_source_file>`. 
  The orchestrator must run Stage 1 policies first. Critical errors must abort code generation with Exit Code 1, except for Stage 3 hardware-limit errors that are explicitly resolved by a valid coarsening plan.

### 3.2 MSL Translation & Syntax Mutation (Source-to-Source)
* REQ-2.2.1: Address Space Qualifier Translation
  The transpiler must map CUDA-specific memory architecture pointers into native MSL address space qualifiers:
    * Raw global pointers (e.g., `float* data`) must be translated to `device float* data [[buffer(N)]]`, where N represents a strictly sequential zero-indexed identifier.
    * Read-only value parameters (e.g., `int width`) must be qualified as constant memory descriptors: `constant int& width [[buffer(M)]]`.
* REQ-2.2.2: Compute Geometry Attribute Injection
  The engine must automatically append native Apple Metal execution attribute variables to the trailing end of every kernel argument signature:
    * `uint3 thread_position_in_grid [[thread_position_in_grid]]`
    * `uint3 threadgroup_position_in_grid [[threadgroup_position_in_grid]]`
    * `uint3 threads_per_threadgroup [[threads_per_threadgroup]]`
    * `uint3 thread_position_in_threadgroup [[thread_position_in_threadgroup]]`
* REQ-2.2.3: Implicit Coordinate Variable Substitution
  The internal block scanner must mutate native CUDA hardware position tokens within function bodies into mathematically equivalent statements derived from the injected MSL attributes (REQ-2.2.2):
    * `threadIdx.x`  --->  `thread_position_in_threadgroup.x`
    * `blockIdx.x`   --->  `threadgroup_position_in_grid.x`
    * `blockDim.x`   --->  `threads_per_threadgroup.x`
    * `__syncthreads()` ---> `threadgroup_barrier(mem_flags::mem_threadgroup)`

### 3.3 Kernel Routing Table Specification
* REQ-2.3.1: Sequential Argument Layout Extraction
  The compilation engine must record the precise sequence and underlying data types of the kernel arguments during code mutation.
* REQ-2.3.2: Containerized Routing Artifact Serialization
  The system must construct a versioned JSON layout named `routing_table.txt`. The schema tracks argument order, memory space, buffer/scalar kind, numeric buffer index, and the Metal entry point.
  This file must be zipped inside `mcu_artifacts.zip` along with the source mapping logs and the newly generated intermediate `.metal` code stream.

```json
{
  "schema_version": 1,
  "translated_kernels": {
    "matriceActivareKernel": {
      "msl_entry_point": "matriceActivareKernel_msl",
      "argument_count": 3,
      "bindings": [
        { "argument_index": 0, "buffer_index": 0, "identifier": "input", "type": "float*", "kind": "buffer", "binding_target": "buffer(0)", "space": "device" },
        { "argument_index": 1, "buffer_index": 1, "identifier": "output", "type": "float*", "kind": "buffer", "binding_target": "buffer(1)", "space": "device" },
        { "argument_index": 2, "buffer_index": 2, "identifier": "size", "type": "int", "kind": "scalar", "binding_target": "buffer(2)", "space": "constant" }
      ],
      "source": { "file": "kernels/matrix.cu", "line": 12 }
    }
  }
}
```

## 4. INTEGRATION VERIFICATION & REPAIR LOGIC

### 4.1 Automated Transpilation Integration Matrix
The tests in `tests/test_stage2_build.py` must validate:

* sequential `[[buffer(N)]]` allocations and address spaces;
* CUDA coordinate and barrier mutation;
* routing-table schema and ZIP contents;
* build abortion when Stage 1 produces an unrecoverable error;
* native compilation of representative generated MSL through `xcrun metal` on macOS.
