# SOFTWARE REQUIREMENTS SPECIFICATION (SRS)
# SYSTEM LAYER: STAGE 7 - NVCC-COMPATIBLE DRIVER, INCREMENTAL BUILDS & MAKE
# -----------------------------------------------------------------------------

## 1. CURRENT BASELINE
Stage 6 can produce and execute a native macOS program, but it is still exposed
as a whole-project prototype command:

  ./mcu build <entry> --native --output <directory>

Measured on the Stage 6 development machine on 2026-06-23:
* Stage 1 analysis: 0.05 s;
* Stage 2/3 translation and artifact packaging: 0.03-0.06 s;
* standalone Metal syntax compilation: 0.03 s;
* clean native build: 2.31-2.55 s;
* process startup, runtime MSL JIT, and one small GPU workload: 0.24 s;
* buffer-allocation p95: 1.667 us;
* full verification: 32 tests in 8.62 s, plus native integration checks.

These are development baselines, not stable cross-machine guarantees. Stage 7
must record machine, SDK, architecture, command, cache state, and repeated samples
before comparing results.

## 2. PROBLEMS THIS STAGE MUST CLOSE
* The CLI has no `compile`, `run`, `make`, or NVCC-driver modes.
* Every native build deletes transformed host output and recompiles all runtime
  Objective-C++ sources, even when no relevant input changed.
* The generated `.air` file is not linked into a `.metallib`; runtime startup
  recompiles `generated.metal` through `newLibraryWithSource`.
* There is no compile/link boundary, `.mcuobj` format, dependency graph, depfile,
  or content-addressed cache.
* Include paths, definitions, optimization flags, output names, and host flags do
  not yet flow through an NVCC-compatible invocation model.
* Existing Makefiles cannot discover MCU as `nvcc` without manual environment
  manipulation.
* Current timing output measures whole commands and cannot isolate frontend,
  device link, Metal compile, host compile, native link, cache lookup, and run.

## 3. OBJECTIVE
Stage 7 turns MCU into a compiler toolchain that existing build systems can call.
It preserves the Makefile as the source of build behavior, intercepts supported
NVCC invocations, compiles translation units into versioned MCU objects, and
links native Mach-O executables with precompiled Metal libraries.

The common workflows become:

  mcu compile src/main.cu src/helper.cu -O2 -o app
  mcu run src/main.cu -O2 -- input.txt
  mcu make -C existing_cuda_project

No Python command, runtime environment variable, or manual artifact extraction
is required after a successful build.

## 4. DRIVER PIPELINE

  mcu make
      |
      +-> create temporary tool directory containing an `nvcc` shim
      +-> prepend only that directory to the child process PATH
      +-> execute the requested `make` command unchanged
              |
              +-> nvcc-compatible argument parser
                      |
                      +-> compile/-dc -> versioned `.mcuobj`
                      +-> link        -> device link + metallib + Mach-O

The shim forwards a structured argument vector to MCU. It must not parse shell
text, rewrite the Makefile, or persistently modify the user's PATH.

## 5. COMPONENT OWNERSHIP
Suggested package boundaries:
* `cli/commands/compile.py`, `run.py`, and `make.py`: user workflows only;
* `core/driver/nvcc.py`: invocation classification and supported flag parsing;
* `core/driver/build_graph.py`: compile/link nodes and dependency edges;
* `core/objects/format.py`: `.mcuobj` schema, validation, and atomic I/O;
* `core/cache/keys.py` and `store.py`: fingerprints and content-addressed storage;
* `core/toolchain/metal.py` and `host.py`: external compiler execution;
* `core/build/linker.py`: final device/native link orchestration;
* `core/integration/make.py`: temporary shim and child-process environment;
* `core/metrics/timing.py`: named phases and cache event collection.

CLI code may orchestrate these services but must not contain translation, cache,
or toolchain policy. The Make integration layer must not import frontend passes.

## 6. CLI CONTRACT
* `mcu compile <inputs...> [flags] -o <output>` builds an executable or object
  according to `-c`/`-dc` and the output suffix.
* `mcu run <inputs...> [flags] -- <arguments...>` builds, then replaces or starts
  the requested program while preserving its exit status.
* `mcu make [-C directory] [make arguments...]` executes the system `make` with
  the temporary shim and returns the same meaningful status.
* Internal `mcu nvcc-driver -- <nvcc arguments...>` is stable enough for the shim
  but is not presented as a general user command.
* `--verbose` prints external commands and cache decisions; default output remains
  concise. Timing data must be available without parsing prose.

## 7. NVCC INVOCATION MODEL
The first supported subset is:
* source inputs: `.cu`, `.c`, `.cc`, `.cpp`, `.cxx`, and `.mcuobj`;
* modes: compile/link, `-c`, and relocatable device code `-dc`;
* paths and definitions: `-I`, `-isystem`, `-D`, and `-U`;
* output and optimization: `-o`, `-O0`, `-O1`, `-O2`, and `-O3`;
* validated host options through `-Xcompiler`;
* dependency output needed by Make: `-M`, `-MM`, `-MD`, `-MMD`, `-MF`, and `-MT`.

Argument order, repeated options, relative paths, and the invocation working
directory must be preserved. Unsupported options are classified as:
* semantic: fail because ignoring them may change the program;
* link-only: forward only when explicitly validated;
* informational: implement or reject predictably.

Silent flag dropping is forbidden.

## 8. MCU OBJECT FORMAT
`.mcuobj` is a deterministic, versioned container, not a renamed native object.
It contains:
* schema, MCU version, runtime ABI, target architecture, and SDK identity;
* normalized invocation and source/dependency fingerprints;
* typed project symbols and the translation-unit device-link contribution;
* transformed host source or a reference to a validated cached host object;
* source maps, diagnostics metadata, required capabilities, and registry version;
* enough information to reject incompatible objects before native linking.

Writes use a temporary file plus atomic rename. Malformed, partial, newer-schema,
wrong-architecture, or wrong-ABI objects produce explicit diagnostics.

## 9. INCREMENTAL BUILD AND CACHE
Cache entries are immutable and content-addressed. Keys include:
* source bytes and transitive project header bytes;
* normalized include paths, definitions, language mode, and relevant flags;
* MCU/compiler registry version and runtime ABI;
* target architecture, macOS SDK identity, Metal version, and host compiler;
* the output-producing pass version.

Cache layers are independent:
1. parsed/semantic translation-unit IR;
2. `.mcuobj` and transformed host translation unit;
3. generated MSL and linked `.metallib`;
4. compiled MCU runtime/native support objects;
5. final native link result when every input is unchanged.

The build graph must recompile only affected translation units. Header dependency
changes invalidate their consumers. Cache corruption becomes a miss, never a
successful build with unverified data. A lock or atomic publish strategy prevents
parallel Make jobs from observing partial entries.

## 10. NATIVE ARTIFACT LAYOUT
The final application must load a precompiled `.metallib`, not compile MSL during
normal startup. The library may be embedded in the executable/bundle or installed
at a deterministic executable-relative path. The chosen policy must survive
moving the complete output directory and must not depend on the repository.

Runtime Objective-C++ code is compiled into a reusable static library or cached
object set keyed by architecture, SDK, optimization, and runtime ABI. User host
translation units remain separate objects so one changed source does not rebuild
the runtime or unrelated files.

Source MSL may remain as an optional debugging artifact. Runtime JIT is an
explicit debug/fallback mode and is reported separately.

## 11. TIMING AND PERFORMANCE BUDGET
Every benchmark reports cold and warm cache separately, at least five warm runs,
median and p95, and named phases. Initial development targets on the current
machine are:
* `mcu check` or translation of the current small examples: p95 <= 0.10 s;
* unchanged no-op `mcu compile`/`mcu make`: p95 <= 0.20 s;
* one changed translation unit in a small project: p95 <= 1.00 s;
* clean current Stage 6-sized native project: p95 <= 3.00 s;
* MCU orchestration overhead on a cache hit: p95 <= 0.05 s, excluding `make`;
* precompiled-library load plus empty/small launch startup: p95 <= 0.05 s;
* normal runtime path performs zero MSL source compilations.

The current 0.24 s run is expected to improve primarily by replacing runtime JIT
with `.metallib` loading. The current 2.31-2.55 s clean build is expected to
improve on warm builds by caching runtime objects and splitting host compilation.

Targets are regression gates for the named fixture and machine class. They are
not claims that MCU matches every NVCC workload or NVIDIA compilation time.

## 12. IMPLEMENTATION MILESTONES

### 7A - Metrics and Invocation Model
* Add named phase timers and cache-state reporting.
* Define typed NVCC invocation and flag diagnostics.
* Add parser fixtures from real compile, `-dc`, dependency, and link commands.

### 7B - Native Compile and Run Commands
* Implement `mcu compile` and `mcu run` over the existing pipeline.
* Preserve output name, program arguments, exit code, and working directory.
* Keep legacy `mcu build --native` operational during migration.

### 7C - MCU Objects and Device Link
* Add deterministic `.mcuobj` serialization and validation.
* Compile translation units independently and combine them at final link.
* Add native host-object input support for the validated subset.

### 7D - Precompiled Metal and Incremental Cache
* Link generated AIR into `.metallib` and load it at runtime.
* Build reusable runtime objects/static library.
* Add dependency-aware layered cache and atomic publication.

### 7E - Make and NVCC Shim
* Implement temporary shim lifecycle and isolated PATH modification.
* Support nested Makefiles, `-C`, generated paths, dependency files, and `-j`.
* Verify cleanup and signal/exit-status propagation.

### 7F - Performance and Compatibility Gate
* Add cold, warm, no-op, and one-file-change benchmark fixtures.
* Build an unchanged multi-file CUDA Makefile with `nvcc -dc`.
* Run the resulting native executable outside the repository environment.

## 13. TEST MATRIX
Unit tests:
* NVCC token parsing, mode classification, and unsupported flags;
* cache-key sensitivity and stability;
* `.mcuobj` round trip, corruption, schema, architecture, and ABI rejection;
* dependency graph invalidation and deterministic link ordering;
* timing phase and cache event serialization.

Integration tests:
* direct compile and run with arguments and nonzero program exit status;
* separate compile/`-dc`/link invocations;
* nested Makefile with relative includes, generated directories, and `make -j`;
* spaces in project paths and repeated `-I`/`-D` options;
* unchanged build, one changed `.cu`, and one changed shared header;
* executable moved with its runtime artifacts and run without MCU environment;
* precompiled `.metallib` path with an assertion that runtime JIT is not called.

Regression tests include every Stage 1-6 test and native SHA-256 execution.

## 14. REQUIRED DIAGNOSTICS
At minimum:
* `UnsupportedNvccFlag` and `InvalidNvccInvocation`;
* `IncompatibleMcuObject` and `CorruptMcuObject`;
* `DependencyScanFailed` and `CacheEntryRejected`;
* `MetalLibraryLinkFailed` and `MetalLibraryLoadFailed`;
* `NativeLinkFailed` and `MakeInvocationFailed`.

Diagnostics include the original argument or source location, build phase,
working directory, and nested tool exit status where applicable.

## 15. EXIT CRITERIA
Stage 7 is complete only when:
* an unchanged nested Makefile invoking `nvcc -dc` builds through `mcu make`;
* compile-only MCU objects are independently produced and linked;
* the native result runs without Python, repository paths, or environment vars;
* normal startup loads a precompiled `.metallib` and performs no MSL JIT;
* no-op and one-file incremental builds demonstrate correct cache reuse;
* unsupported semantic NVCC flags fail explicitly;
* the timing budget is measured and regressions are visible in `make verify`.
