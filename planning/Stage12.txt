# SOFTWARE REQUIREMENTS SPECIFICATION (SRS)
# SYSTEM LAYER: STAGE 12 - STABLE TOOLING API & IDE INTEGRATION
# -----------------------------------------------------------------------------

## 1. OBJECTIVE
Stage 12 freezes the machine-facing MCU contract and exposes compiler services to
editor tooling without coupling compiler internals to a specific IDE.

## 1.1 KNOWN PROBLEMS TO CLOSE
* Current human output is useful interactively but phase timings, cache events,
  capabilities, and diagnostics are not a frozen machine-readable contract.
* Repeated IDE checks would pay process and frontend startup unless a service or
  reusable project state is introduced.
* Schema stability can slow internal refactoring unless versioning and adapters
  are owned at serialization boundaries.

## 2. JSON CONTRACTS
Versioned schemas are required for check, build, compile, run, make, diagnostics,
capabilities, artifacts, cache events, and timing metrics. With `--json`, stdout
contains exactly one JSON document and human logs use stderr when needed.

## 3. CAPABILITY REPORT
Expose supported CUDA syntax, types, qualifiers, intrinsics, runtime APIs, NVCC
flags, architecture constraints, and library adapters. Each entry includes status,
supported signatures, target requirements, and the stage that introduced it.

## 4. PROCESS CONTRACT
* Exit 0: successful operation.
* Exit 1: source, semantic, translation, or native compilation failure.
* Exit 2: invalid invocation, missing toolchain, filesystem, or infrastructure error.
* Cancellation and timeout behavior must be explicit and machine-readable.

## 5. IDE BACKEND
Provide stable requests for project analysis, diagnostics, capability lookup,
build progress, and source-map navigation. Transport may be subprocess JSON or a
long-running service, but compiler packages must not import editor-specific code.

## 6. ACCEPTANCE
* Contract fixtures detect accidental schema changes.
* Diagnostics remain stable across human and JSON output modes.
* A reference VS Code client can analyze and build without parsing terminal text.
* All Stage 1-11 command-line workflows remain available without an IDE.

## 7. PERFORMANCE BUDGET AND MEASUREMENT
* Warm incremental analysis response for the current small fixture: p95 <= 0.10 s.
* Capability lookup from a warm service/cache: p95 <= 0.02 s.
* JSON serialization must consume <= 10% of total command time for normal build
  responses; large diagnostics/artifacts are referenced rather than embedded.
* A long-running backend must remain bounded during a 1,000-edit stress test and
  report project-state/cache memory; no monotonic unbounded growth is accepted.
* CLI commands retain Stage 7-11 timing gates. IDE transport is measured
  separately from compiler work.
