# SOFTWARE REQUIREMENTS SPECIFICATION (SRS)
# SYSTEM LAYER: STAGE 4 - C++ RUNTIME WRAPPER, UNIFIED MEMORY GATEWAY & METAL DISPATCH
# -----------------------------------------------------------------------------

## 1. MODULE OVERVIEW & ARCHITECTURAL OBJECTIVES
The primary objective of Stage 4 is to build the native runtime bridge that maps standard NVIDIA CUDA Host API operations and execution configuration syntaxes (triple-chevron bounds) directly into the Apple Metal Compute Framework. 

This module leverages Apple Silicon's Unified Memory Architecture (UMA) to completely eliminate discrete PCIe bus transmission overheads. It uses the `routing_table.txt` artifact compiled in Stage 2/3 to dynamically bind pointers to strict hardware buffer lanes at runtime without ahead-of-time linking.

## 2. RUNTIME GRAPH ARCHITECTURE
The runtime wrapper translates state calls on the host CPU into immediate state evaluation and commands on the Apple GPU:

  [CUDA API Call] ---> cuda_to_metal.h ---> 1. Runtime JSON Parser (Extracts routing data)
                                      ---> 2. UMA Buffer Gateway (Zero-copy allocation)
                                      ---> 3. Dynamic Pipeline Dispatcher (MTLComputeCommandEncoder)

### 2.1 Component Definitions:
* runtime/include/cuda_to_metal.h: The public C++17 emulation header. Contains CUDA-compatible types, memory shims, typed argument packing, and the cudaLaunch macro.
* runtime/src/runtime_core.mm: The Objective-C++ backend. Initializes Metal, manages shared buffers, parses routing metadata, compiles MSL, and dispatches pipelines.
* core/host_transpiler.py: Rewrites triple-chevron launches and removes device-only kernel code from host compilation units.

The CLI extracts runtime inputs into the native build directory. The ZIP remains an unencrypted transport artifact and is not parsed by the runtime process.

## 3. DETAILED FUNCTIONAL REQUIREMENTS

### 3.1 Unified Memory Architecture (UMA) Gateway
* REQ-4.1.1: Zero-Copy Storage Mapping
  `cudaMalloc(void** devPtr, size_t size)` must use `newBufferWithLength` with `MTLResourceStorageModeShared`.
* REQ-4.1.2: Virtual Direct Memory Pointer Access
  The memory copy abstraction `cudaMemcpy(void* dst, const void* src, size_t count, cudaMemcpyKind kind)` must evaluate transmission boundaries:
    * Host-to-Device and Device-to-Host operations use direct memcpy/memmove against `MTLBuffer.contents`.
    * Virtual transfers must avoid discrete staging buffers to maintain zero-copy operations.
* REQ-4.1.3: Allocation Lifecycle
  The gateway must expose cudaFree and maintain a pointer-to-Metal-buffer registry, including offsets into allocations. cudaDeviceSynchronize and cudaGetLastError expose completion and failures.

### 3.2 Dynamic Pipeline Loading & Kernel Dispatch
* REQ-4.2.1: On-the-Fly Just-In-Time (JIT) MSL Compilation
  On first dispatch, the runtime loads `generated.metal` and `routing_table.txt` from the native build directory, compiles MSL with `newLibraryWithSource`, and caches each compute pipeline.
* REQ-4.2.2: Automated Schema-Driven Argument Binding
  When a kernel dispatch is intercepted via emulated layout calls, the runtime engine must read the specific function's array blocks within the JSON routing table. For each argument:
    * If `space` equals `"device"`, bind the registered Metal buffer and pointer offset to numeric `buffer_index`.
    * If `space` equals `"constant"`, inject the raw scalar byte-stream directly using `setBytes`.

### 3.3 Threads Virtualization Enforcement
* REQ-4.3.1: Coarsening Geometry Realignment
  The runtime executor must intercept the requested execution configuration block size ($DimX, DimY, DimZ$). Before calling `dispatchThreadgroups`, it must check the `optimization_metrics` block from the extracted routing metadata:
    * The physical grid threadgroup configuration size passed to Metal must map exactly to the altered `physical_block` layout array.
    * The host runtime divides only block.x by `coarsening_factor`; grid dimensions remain unchanged.
    * Coarsened dispatch must match recorded original block geometry and remain inside the pipeline threadgroup limit.

### 3.4 Native Host Build
* REQ-4.4.1: Host Syntax Transformation
  MCU rewrites triple-chevron and cudaLaunch forms into typed runtime calls before invoking clang++.
* REQ-4.4.2: Native Output Contract
  `mcu build <path> --native --output <directory>` emits runtime artifacts, transformed host sources, and an executable linked with Metal and Foundation.

## 4. INTEGRATION TESTING & NUMERIC EQUIVALENCE CONTRACT

### 4.1 Native macOS Numerical Verification Suite
To confirm compilation and mathematical safety, the suite must run verification contracts matching calculations against reference layouts:
* `examples/stage4_numeric/main.cu` allocates 100,000 floats, runs an automatically coarsened Metal kernel, and compares output with CPU simulation at $\epsilon \le 10^{-6}$.
* The same executable warms allocation, reports p95 over 200 measured iterations, and requires p95 below 2ms.
* `tests/test_stage4_native_runtime.py` builds and executes the contract; repeated allocate/free operations validate lifecycle success. Latency alone is not proof of leak freedom.
