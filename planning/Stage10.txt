# SOFTWARE REQUIREMENTS SPECIFICATION (SRS)
# SYSTEM LAYER: STAGE 10 - ASYNCHRONOUS STREAMS & COMMAND SCHEDULING
# -----------------------------------------------------------------------------

## 1. OBJECTIVE
Stage 10 replaces synchronous per-launch waiting with a stream-aware scheduler
while preserving CUDA ordering, error, copy, and resource-lifetime contracts.

## 2. SCOPE
Included:
* default and explicitly created streams;
* asynchronous kernel launch through CUDA's fourth launch configuration value;
* cudaMemcpyAsync for the validated synchronous copy kinds;
* stream/device synchronization and deferred Metal errors;
* deterministic resource retention and opt-in scheduler metrics;
* easy, medium, hard, and stress workloads used as Stage 14 baselines.

Excluded:
* events and inter-stream event dependencies;
* priorities, callbacks, per-thread default streams, capture, and CUDA Graphs;
* a promise of physical overlap on every Apple GPU;
* algorithm-specific optimization.

## 3. RUNTIME ARCHITECTURE
* StreamRegistry owns opaque handles, one Metal command queue per explicit stream,
  the default stream, pending command buffers, and deferred copy state.
* KernelDispatcher validates and encodes one launch but never waits for it.
* SynchronizationService drains one or every stream, resolves deferred D2H copies,
  collects GPU timestamps, and maps failures to their originating operation.
* BufferRegistry resolves validated MTLBuffer ranges for asynchronous blits.
* cudaFree synchronizes outstanding work before releasing a registered allocation.
  A future asynchronous allocator may relax this without changing correctness.

## 4. ORDERING CONTRACT
* Operations submitted to one stream execute in submission order.
* Explicit non-default streams do not acquire ordering against each other.
* Legacy default-stream semantics are conservative: default work waits for prior
  explicit-stream work, and explicit-stream work waits for prior default work.
* cudaStreamSynchronize waits only for the selected stream.
* cudaDeviceSynchronize and synchronous memory copies drain all streams.
* Destroying a stream synchronizes it before invalidating its handle.

## 5. COPY CONTRACT
* H2D async copies snapshot host input into a retained Metal staging buffer.
* D2D async copies use an ordered Metal blit.
* D2H async copies blit into retained staging and publish to the host pointer when
  the owning stream is synchronized; the caller must keep host memory alive.
* H2H async copies are rejected because pageable-host async semantics are outside
  the supported subset.
* Invalid ranges, kinds, streams, and overlapping D2D ranges fail immediately.

## 6. TEST PYRAMID
* easy: lifecycle, one stream, one async copy, one producer/consumer chain;
* medium: default-stream ordering, two independent streams, device-wide wait;
* hard: 100-1,000 launches, mixed copies/kernels, multiple buffers and streams;
* stress: repeated create/destroy/free and deferred-error/resource-lifetime cases.

Correctness fixtures stay in this repository because they gate compiler commits.
Large application corpora and long-running comparative benchmarks may move to a
separate repository after the report schema stabilizes.

The checker command is:

```text
python scripts/cuda_checker.py --tier all
```

It discovers 20 manifests under `tests/cuda_suite/cases`, compiles each unique
CUDA program once, runs cases from easy through stress, prints PASS/FAIL, and
writes `/tmp/mcu_cuda_checker.json` by default.

## 7. PERFORMANCE AND STAGE 14 DATA
The Stage 10 benchmark emits versioned JSON with workload tier, launch count,
stream count, synchronous wall time, batched wall time, speedup, command-buffer
count, CPU submission, GPU execution, synchronization wait, and device identity.

Budgets:
* 100 tiny batched launches should reduce submission-plus-wait wall time by at
  least 25% versus synchronizing every launch, or report the platform limit;
* one warmed large kernel must not regress by more than 10%;
* Stage 9 clean/no-op/incremental and startup budgets remain green;
* overlap is measured, never asserted as portable correctness.

## 8. ACCEPTANCE
* CUDA fourth-configuration stream syntax lowers to the typed runtime API.
* Producer/consumer chains are exact in one stream.
* Two explicit streams make progress without accidental mutual synchronization.
* Async H2D/D2D/D2H copies preserve ordered values.
* Device synchronization drains every stream.
* Free/destroy stress tests have no use-after-free or lost deferred error.
* The multi-launch benchmark is deterministic and records Stage 14 input data.
* All Stage 1-9 regressions remain green.

## 9. IMPLEMENTATION REPORT - 2026-06-24
Implemented:
* opaque CUDA stream handles and lifecycle APIs;
* one ordered Metal queue per explicit stream plus legacy default-stream policy;
* asynchronous kernel submission with deferred command-buffer completion;
* fourth-value CUDA launch lowering with independent shared-byte propagation;
* ordered H2D/D2D/D2H blits with retained staging buffers;
* stream and device synchronization, deferred D2H publication, GPU timestamps,
  originating-operation diagnostics, and safe synchronize-before-free behavior;
* dynamic routing metadata validation for runtime-known launch geometry;
* runtime ABI 3 and MCU version 0.10.0;
* Stage 14 scheduler baseline collector and a separate 20-case CUDA checker.

Final full-gate scheduler baseline on Apple M4 Max, five samples per tier:
* 10 launches: 3.172x median speedup, 2.309 ms vs 0.620 ms;
* 100 launches: 5.792x median speedup, 12.856 ms vs 2.220 ms;
* 1,000 launches: 10.471x median speedup, 105.730 ms vs 9.909 ms;
* one million-element launch-only case: 1.079x, no large-kernel regression;
* all Stage 10 performance budgets passed;
* complete repository suite: 76 tests passed in 33.24 s;
* CUDA checker: 20/20 easy, medium, hard, and stress cases passed.

Repository policy:
* semantic regression cases and short performance baselines remain here and gate
  the compiler commit that changes them;
* a future separate repository should contain large third-party applications,
  long-duration benchmarks, hardware comparison history, and private workloads;
* both repositories can consume the versioned checker/metrics JSON contracts.
